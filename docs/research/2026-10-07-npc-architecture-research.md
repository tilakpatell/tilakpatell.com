# NPC architecture: action lifecycles, deterministic simulation, AI scheduling, the browser's execution model, and where the GPU helps

Date: 2026-10-07. The third research note behind the NPCs. The first, `2026-10-07-game-ai-npcs.md`, settled how the brains decide, perceive, search, steer and act as squads (utility, trees, target tracks, context steering, influence maps, attack tokens); the second, `2026-10-06-beyond-webgl-webgpu-and-living-worlds.md` (on PR #371's branch), settled what three r186's WebGPU build gives, that compute is WebGPU-only, and the three ways to put a language model behind a character. This note covers what neither did and the design `docs/superpowers/specs/2026-10-07-npc-architecture-design.md` leans on: how an action lives and dies against its animation, how a simulation stays reproducible and debuggable, how a hundred brains share a frame, what a static site's browser can and cannot run off the main thread, what three r186 does and does not do for crowds, what a game owes a keyboard and a screen reader, and how a language model's answer is kept inside the game's rules.

## The verdict first

1. **An action is an object with a lifecycle, not a mode string.** Unreal's abilities (activate, commit, end or cancel, with tags that block and tags that cancel), Unity's transition interruption sources (none, by the source, by the destination) and Anguelov's start / execute / stop split for animation behaviours are three statements of one shape. The site's brains emit `mode`; the gap is the thing that runs between a mode being chosen and its body finishing: what it needs, when it can be cut, what it does when cut, what it does when it fails. That shape is `lib/ai/action.js`.
2. **The simulation steps on a fixed clock; the picture interpolates.** Fiedler's accumulator with a clamp, and inputs and random inside the step, is what makes a run replayable from a seed and an input log. Mario 64 (30 Hz), Portal panic (120 Hz), the Battlefront (10 Hz substeps) and Minecraft (20 Hz) each have their own copy; the universe, the surface, Cybertron and the watchers step on the frame's `dt`. One `lib/sim/fixedStep.js` and one PCG-style seeded stream per world and per agent make every brain reproducible.
3. **Record before you make deterministic.** Treyarch's lesson: retrofitting determinism is slow; a fixed-size ring buffer of each agent's state and decision after every step costs nothing, holds ten seconds, and gives a scrubbing overlay at once. That is `lib/ai/trace.js` and the inspector.
4. **Update rates come from a budget and a significance score, not from distance rings.** The LOD Trader and Unreal's Significance Manager: score every agent by how much a visitor would notice it (on screen, size on screen, recently met), rank, and spend a fixed millisecond budget from the top. That is `lib/ai/schedule.js`, the brains' twin of `lib/three/animBudget.js`.
5. **The AI stays on the main thread, in JS.** A hundred brains at 10 Hz is well under a millisecond a frame; the measured costs on this site are the mixers and the draws, not the deciding. A worker would need transferable snapshots every tick (GitHub Pages cannot set the COOP/COEP headers `SharedArrayBuffer` needs, so there is no shared memory), and a compute pass is WebGPU-only on a site with no WebGPU world yet. The scheduler's `stats()` is the measurement that would change this verdict: a worker becomes worth it only if `ai.ms` passes 4 ms on the mid tier.
6. **The GPU's job for characters is skinning and instancing, which it already does.** three r186 has no instanced skinning in `InstancedMesh`; the WebGPU example shares one skeleton across instances. Crowds beyond the animator's budget are the W2+ waves' instanced far figures, not an AI concern.
7. **The language model stays an experiment.** Where it is wanted, the contract is a schema-constrained `{ say, mood, action }` that game code still validates (OWASP LLM01), with the baked lines as the floor and a timeout to them. Nothing in the essential scope depends on it.

## 1. Animation-aware actions & interruption

- **Understanding the Unreal Engine Gameplay Ability System** — https://dev.epicgames.com/documentation/en-us/unreal-engine/understanding-the-unreal-engine-gameplay-ability-system. An ability has an explicit lifecycle: Activate (in-progress), Commit (last chance to fail: spend cost, start cooldown), then EndAbility or Cancel "to stop it mid-execution". Every ability carries tag lists: tags it grants its owner while active, tags that *block* its activation, and tags that *auto-cancel* it when they appear; montage playback is an async "ability task" inside the ability. *Applies:* model NPC actions as `{canActivate(tags), commit(), tick(), cancel(reason), end()}` with granted/blocked/cancelled-by tag sets, so "stagger" cancels "attack" declaratively instead of via per-action if-chains.
- **UAnimMontage BlendOut / Montage_Stop (Unreal API)** — https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/UAnimMontage. `BlendOut` is used only when the montage ends by itself; "if it's interrupted by other montages, it will use the new montage's BlendIn option to blend out." `BlendOutTriggerTime` fires the blend-out before the clip ends so the next pose arrives as the clip finishes; `OnInterrupted` vs `OnBlendOut` are separate callbacks. *Applies:* give each clip-backed action a `blendOutTriggerTime` and let the *incoming* action's fade-in own the crossfade duration; surface `interrupted` and `completed` as distinct outcomes to the planner.
- **Unity `TransitionInterruptionSource` (Animator state transitions)** — https://docs.unity3d.com/ScriptReference/Animations.TransitionInterruptionSource.html. A running transition is either `None` ("cannot be interrupted. Formerly known as Atomic"), or interruptible by transitions from the `Source` state, the `Destination` state, or both in a fixed order (`SourceThenDestination` / `DestinationThenSource`). *Applies:* a per-action "interruptible by" policy (none / by same layer / by higher-priority layer) is a tiny enum, not a general-purpose graph; adopt it as the action-cancel rule.
- **Unity Animation Layers & Avatar Masks** — https://docs.unity3d.com/Manual/AnimationLayers.html. Layers split the skeleton: a mask limits a layer to e.g. the upper body so a throw plays over walk/run/idle; each layer blends `Override` ("replace the animation on previous layers") or `Additive` ("add on top of previous layers"), with a layer weight. *Applies:* three.js has no masks, so emulate the upper-body layer by splitting the clip's tracks by bone name into a second `AnimationClip` (see next item) and running it as a separate action with its own weight.
- **three.js `AnimationAction` / `AnimationUtils.makeClipAdditive`** — https://threejs.org/docs/pages/AnimationAction.html and https://threejs.org/docs/pages/AnimationClip.html. Natively three supports per-action `weight`, `fadeIn/fadeOut/crossFadeTo`, `warp`, `halt`, `clampWhenFinished`, `syncWith`, and `blendMode = AdditiveAnimationBlendMode` — but `makeClipAdditive(clip, referenceFrame=0, referenceClip)` is mandatory first ("makes each track's values relative to the values at the reference frame"). The docs contain no per-bone mask or partial-body feature; blending is whole-action. *Applies:* additive hit-react / breathing / look offsets are first-class; partial-body layering must be done by track-splitting clips (bone-name filter) at load time, once per NPC kind, then driven as a parallel action.
- **Bobby Anguelov, "Separation of Concerns Architecture for AI and Animation" (Game AI Pro 2, ch. 12)** — https://www.gameaipro.com/GameAIPro2/GameAIPro2_Chapter12_Separation_of_Concerns_Architecture_for_AI_and_Animation.pdf. Argues against reusing the gameplay FSM for animation: lifetimes don't map 1:1 and gameplay gains code/data dependencies on blend-tree internals. Instead an *animation behavior* layer (below gameplay, no access to it) runs each visual action in three stages — "start" (get the graph into a state where execute can proceed, e.g. wait for idle→move), "execute" (drive parameters), "stop" (clean up and return the graph to a neutral state other behaviors can continue from) — with animation *events* bubbling back up. *Applies:* exactly the boundary for this repo: AI emits intents (`moveTo`, `attack`, `emote`), an animation-behavior layer owns clip selection, start/execute/stop and reports `started/finished/interrupted` events; AI never touches `AnimationMixer`.

## 2. Deterministic simulation, fixed timestep, replay

- **Glenn Fiedler, "Fix Your Timestep!"** — https://gafferongames.com/post/fix_your_timestep/. Accumulate frame time, clamp it (`if (frameTime > 0.25) frameTime = 0.25;` to avoid the spiral of death), step the simulation in fixed `dt` chunks in a `while` loop, and render an interpolated state with `alpha = accumulator / dt` between previous and current states. A fully fixed `dt` is what makes a run "exactly reproducible given the same inputs". *Applies:* run NPC AI + movement at a fixed 30 or 60 Hz tick independent of rAF, keep prev/current transforms per entity, and interpolate on render; the clamp matters on tab-return (see §4).
- **Fiedler, "Deterministic Lockstep"** — https://gafferongames.com/post/deterministic_lockstep/. Determinism means sending only inputs and re-simulating; any float-ordering, iteration-order or time-source divergence breaks it. *Applies:* even single-player, a deterministic sim lets a bug report be "seed + input log" rather than a video; keep all randomness and time inside the sim step and never read `Date.now()`/`Math.random()` from AI code.
- **PCG family (pcg-random.org)** — https://www.pcg-random.org/. Small-state LCG + output permutation; the comparison table lists "Reproducible Results: Yes" and "Multiple Streams (e.g. 2^63)" so each subsystem/NPC can own an independent, seedable stream. *Applies:* implement PCG32 (or xoshiro128**) in JS with `Math.imul`/`>>>` and give each world and each NPC its own stream from `(worldSeed, npcId)`, so one NPC's behaviour replays identically regardless of spawn order.
- **David Young, "Debugging AI with Instant In-Game Scrubbing" (Game AI Pro 3, ch. 6, Treyarch)** — https://www.gameaipro.com/GameAIPro3/GameAIPro3_Chapter06_Debugging_AI_with_Instant_In-Game_Scrubbing.pdf. Notes that "retrofitting determinism into an engine which currently is not deterministic is nontrivial", so instead an in-game recorder stores, after each sim frame, one packet per object ("position, orientation, joint matrices, and visibility") in a fixed-size ring buffer that evicts the oldest frames; a recorder controller lets you pause, rewind, step frames and select an object to show its debug info. Requirements: near-zero sim cost, fixed memory, no effect on simulation outcome. *Applies:* a cheap first step before full determinism: a ring buffer of per-NPC `{pos, yaw, state, chosenAction, topScores}` for the last ~10 s, with a dev overlay that scrubs it.

## 3. Scalable AI update scheduling

- **Ben Sunshine-Hill, "Phenomenal AI Level-of-Detail Control with the LOD Trader" (Game AI Pro, ch. 14)** — http://www.gameaipro.com/GameAIPro/GameAIPro_Chapter14_Phenomenal_AI_Level-of-Detail_Control_with_the_LOD_Trader.pdf. Distance thresholds can't respect a CPU budget when NPCs cluster. Define a "Break in Realism (BIR)": "a BIR only occurs when the player notices"; categorize BIRs (unrealistic state, fundamental discontinuity, unrealistic long-term behaviour), compute a per-character *criticality* as a product of factors (visibility, distance, attention, recency), then each frame solve a knapsack-style trade of detail levels across all AI features to maximize realism under the budget, "in tens of microseconds". *Applies:* replace "update NPCs within 30 m every frame" with a budget-driven scheduler: score = on-screen × screen-size × recently-interacted; the highest-scoring N get full utility-AI at tick rate, the rest get decayed rates and cheaper steering.
- **Unreal Engine Significance Manager** — https://dev.epicgames.com/documentation/en-us/unreal-engine/significance-manager-in-unreal-engine. Objects register with a game-written significance function (object + viewer transform → float); `Update` is called once per frame by the game, sorts objects, and a post-significance callback lets each object react, e.g. "shutting off Components like Particle Emitters, or by running complex AI code less frequently", including per-type budgets ("at most N characters at the highest tier"). Mass LOD similarly emits High/Medium/Low/Off plus a 0–3 significance float. *Applies:* one `SignificanceManager.update(camera)` per frame producing a tier per NPC; tier → AI tick interval, steering quality, animation mixer update rate, and whether the mesh is instanced-only.

## 4. Browser execution model

- **MDN: Using Web Workers — transferable objects** — https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers. Messages are structured-cloned (copied); `postMessage(buf, [buf])` transfers an `ArrayBuffer` zero-copy and the sender's copy is "cleared and no longer usable". *Applies:* the only no-header way to move NPC state between a sim worker and the render thread is ping-ponging transferable `Float32Array` snapshots (pos/quat/animState per NPC) each tick — double-buffer two buffers so neither side ever waits on a copy.
- **MDN: `SharedArrayBuffer` security requirements** — https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/SharedArrayBuffer. Shared memory needs the document to be cross-origin isolated via `Cross-Origin-Opener-Policy` + `Cross-Origin-Embedder-Policy` headers and a secure context; without them `postMessage()` of a SAB throws, and `crossOriginIsolated` is false. **GitHub Pages cannot set these:** the open GitHub Community discussion #13309 (https://github.com/orgs/community/discussions/13309) has staff stating "This is a scenario we would support with custom headers. No ETA", still unresolved. *Applies:* design for transferables, not SAB/Atomics; the `coi-serviceworker` hack (reload-on-first-visit) is possible but fragile for a portfolio landing — treat SAB as opt-in enhancement only.
- **MDN: `OffscreenCanvas`** — https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas. `canvas.transferControlToOffscreen()` hands the canvas to a worker, which gets a `webgl`/`webgl2` (and `webgpu`) context and can call `requestAnimationFrame` itself; events (`contextlost/contextrestored`) exist but DOM input must still be forwarded from the main thread. *Applies:* the inverse split — rendering in a worker, React/DOM on main — is viable, but three.js scene graph, loaders and input forwarding all move; the simpler win is sim-in-worker, render-on-main.
- **MDN: `requestAnimationFrame` + Page Visibility API** — https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame and https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API. rAF "calls are paused in most browsers when running in background tabs or hidden iframes"; its rate follows the display (60/75/120/144 Hz), so step by the timestamp argument. Hidden tabs also get throttled timers (budget throttling after ~30 s, 10 s in Chrome); `visibilitychange` is the hook to pause audio/sim and resume cleanly. *Applies:* on `hidden`, stop the fixed-step loop and drop the accumulator; on `visible`, resume with the Fiedler clamp so NPCs don't fast-forward 5 minutes of sim.
- **MDN: Prioritized Task Scheduling API (`scheduler.postTask` / `scheduler.yield`) and `requestIdleCallback`** — https://developer.mozilla.org/en-US/docs/Web/API/Prioritized_Task_Scheduling_API and https://developer.mozilla.org/en-US/docs/Web/API/Window/requestIdleCallback. `postTask` takes `user-blocking` / `user-visible` (default) / `background` priorities, a `TaskSignal` for abort/re-prioritise and a `delay`; `scheduler.yield()` breaks long tasks; available in workers too. `requestIdleCallback` gives `deadline.timeRemaining()`, "may not run in busy frames", needs a `timeout` for required work, and is not in Safari. *Applies:* run pathfinding/path smoothing, perception rebuilds and influence-map refreshes as `background` tasks with a `scheduler`→`requestIdleCallback`→`setTimeout(0)` fallback chain, never inside the render callback.

## 5. three.js r186 specifics

- **three.js `InstancedMesh` and closed PR #22667 "InstancedSkinnedMesh"** — https://threejs.org/docs/pages/InstancedMesh.html and https://github.com/mrdoob/three.js/pull/22667. `InstancedMesh` extends `Mesh`; the docs expose `instanceMatrix`, `instanceColor`, `setMorphAt` (per-instance morph weights via a morph texture) and no skinning. The PR adding `InstancedSkinnedMesh` was closed unmerged ("closing this to bring it back more comprehensive"); maintainers objected to another mesh class and noted the real cost is filling the bone texture for all instances. *Applies:* for WebGL, instanced *skinned* crowds need a user-land bone-texture per instance (or `@three.ez/instanced-mesh`); cheaper path for 100 NPC kinds: instanced static/morph-animated low-LOD far away, full `SkinnedMesh` only for the significance tier-1 set.
- **three.js example `webgpu_skinning_instancing`** — https://threejs.org/examples/webgpu_skinning_instancing (source: https://github.com/mrdoob/three.js/blob/dev/examples/webgpu_skinning_instancing.html). The official WebGPU route: the example flags a `SkinnedMesh` child `isInstancedMesh = true // TODO: Resolve this hack`, attaches an `instanceMatrix` with `instanceCount = 30`, and one `AnimationMixer` drives one skeleton shared by all instances. *Applies:* on the WebGPU renderer you can batch identical-pose crowds for free; per-instance animation phase still requires TSL work, so expect "same animation, different offset" rather than independent animation per instance without custom nodes.
- **three.js `BatchedMesh`** — https://threejs.org/docs/pages/BatchedMesh.html. One draw call for many *different* geometries sharing one material: `addGeometry()` then `addInstance(geomId)`, per-instance `setMatrixAt/setColorAt/setVisibleAt/setGeometryIdAt`, built-in `perObjectFrustumCulled` and `sortObjects`, with `optimize()` to repack. *Applies:* world props and NPC-held items (hats, tools, signs) across one atlas material collapse to a single draw per world; no skinning.
- **three.js `TimestampQueryPool` / `WebGPUTimestampQueryPool`** — https://threejs.org/docs/pages/TimestampQueryPool.html and https://threejs.org/docs/pages/WebGPUTimestampQueryPool.html. The renderer (WebGL via `EXT_disjoint_timer_query_webgl2`, WebGPU via timestamp queries) allocates a query pair per render context, `trackTimestamp` defaults true, and `renderer.resolveTimestampsAsync(THREE.TimestampQuery.RENDER)` after `renderAsync` resolves GPU ms into `renderer.info.render.timestamp`. *Applies:* a dev HUD can show real GPU frame time per world on the new renderer — use it to set the per-world triangle/draw budgets rather than guessing from CPU-side `performance.now()`.

## 6. Accessibility & input for browser games

- **Xbox Accessibility Guideline 107: Input** — https://devdocs.xbox.com/build/game-principles/accessibility/xag-deep-dives/xag-107-input.md (index: https://learn.microsoft.com/en-us/gaming/accessibility/guidelines). "Games provide in-game remapping of all controls, regardless of platform-level remapping", per-stick axis inversion, "ideally, actions can be assigned to any input — not just swapped", and "remapped bindings update hints, tips, tutorials, and controller diagrams"; XAG 117 covers motion settings (camera, FOV), and XAG text guidance asks for scalable functional text. *Applies:* keep an `action → [inputs]` map as data, render on-screen prompts from it, and expose a settings panel with remap, invert-Y, FOV, camera-bob off and text scale.
- **MDN: `prefers-reduced-motion`** — https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion. Values `no-preference` / `reduce`; query from JS with `matchMedia("(prefers-reduced-motion: reduce)")`; guidance is to replace large scaling/panning/parallax with dissolves and shorten transitions while keeping feedback. *Applies:* default camera shake, head-bob, screen-space parallax and world-transition zooms to off when `reduce` matches, and let the in-game toggle override.
- **MDN: Pointer Lock API** and **Using the Gamepad API** — https://developer.mozilla.org/en-US/docs/Web/API/Pointer_Lock_API and https://developer.mozilla.org/en-US/docs/Web/API/Gamepad_API/Using_the_Gamepad_API. `requestPointerLock({ unadjustedMovement: true })` needs a user gesture, Esc always exits, listen to `pointerlockchange/pointerlockerror`, read `movementX/Y`. Gamepads expose no button events: poll `navigator.getGamepads()` in the frame loop; Firefox only exposes a pad after the user touches it; `mapping === "standard"` gives a known layout. *Applies:* treat lock loss (Esc, tab switch) as a pause event; poll the gamepad inside the same fixed-step input sampler so it is replay-recordable.
- **WHATWG HTML Standard, canvas "Best practices"** — https://html.spec.whatwg.org/multipage/canvas.html#best-practices. Authors "must also provide content that … conveys essentially the same function or purpose as the canvas's bitmap" as canvas fallback content; interactive regions should map 1:1 to focusable fallback elements, and `drawFocusIfNeeded()` draws a focus ring for the focused fallback element. *Applies:* give the three canvas an `aria-label` plus live-region text ("You are in the Garden world; 3 NPCs nearby") and keep all menus/dialogue as real DOM so screen readers and keyboard focus work.

## 7. LLM NPC safety

- **OWASP Top 10 for LLM Applications 2025 — LLM01: Prompt Injection** — https://genai.owasp.org/llmrisk/llm01-prompt-injection/. Mitigations: constrain model behaviour in the system prompt; "define and validate expected output formats … using deterministic code"; input/output filtering; least privilege ("handle these functions in code rather than providing them to the model"); segregate untrusted content; adversarial testing. Related: LLM05 Improper Output Handling and LLM07 System Prompt Leakage. *Applies:* player text is untrusted input; the LLM only *proposes* `{say, mood, action}` and game code decides whether `action` is allowed for that NPC in that state.
- **Anthropic docs: Structured outputs** — https://platform.claude.com/docs/en/build-with-claude/structured-outputs. `output_config.format = { type: "json_schema", schema }` constrains decoding so output "will match your schema" — except on `stop_reason: "refusal"` or `"max_tokens"`, and enum string casing is not guaranteed (compare case-insensitively). Every object needs `additionalProperties: false`; `enum`/`const`, `required`, `anyOf` are supported; `min/maxLength`, numeric bounds and recursion are not. *Applies:* schema `{say: string, mood: enum[...], action: enum[...]}`; clamp `say` length and allowed actions in code (schema can't), treat refusal/max_tokens as "fallback to local canned line", and do the same validation on WebLLM output, which has no constrained decoding guarantee.

## What this changes for the design

1. Actions become GAS-style objects with tag-driven block/cancel rules and a Unity-style `interruptibleBy` enum; the animation layer reports `started/finished/interrupted` back to AI (Anguelov start/execute/stop).
2. Upper-body layering is done by splitting clip tracks per bone at load; additive clips must go through `makeClipAdditive` — three has no masks.
3. The sim runs on a fixed step with accumulator clamp and render interpolation; `visibilitychange` resets the accumulator.
4. All randomness comes from per-NPC PCG streams seeded from `(worldSeed, npcId)`; no `Math.random()`/`Date.now()` in AI code.
5. Ship a ring-buffer recorder + scrub overlay first; full determinism is a later milestone.
6. NPC update rates come from a significance score and a CPU budget (LOD Trader / Significance Manager), not distance rings.
7. Sim-in-worker uses double-buffered transferable `Float32Array`s; SAB is impossible on GitHub Pages without a service-worker hack, so it is never a hard dependency.
8. Expensive AI work (paths, influence maps) goes to `scheduler.postTask('background')` with `requestIdleCallback`/`setTimeout` fallbacks.
9. Rendering tiers: full `SkinnedMesh` for the top tier, `InstancedMesh` + morph/shared-pose for crowds (WebGPU example path), `BatchedMesh` for props; verify budgets with `TimestampQueryPool`.
10. Input is a remappable action map (XAG 107) sampled in the fixed step (gamepad polling, pointer lock); reduced-motion defaults off camera effects; the LLM returns schema-constrained `{say, mood, action}` that game code still validates, with a local fallback on refusal/timeout.
