# Rebuilding the Frostbite Worlds GPU-First on WebGPU

Date: 2026-10-11. The research behind `docs/superpowers/specs/2026-10-11-gpu-first-renderer-design.md`: seven notes (Unreal Engine 5’s renderer system by system, WebGPU in October 2026, three r186’s node renderer and TSL, Rapier and web physics, WebAssembly, the best 2025 to 2026 web titles, image quality) and the repository’s own numbers of the day, synthesised into one report. Every external claim carries its link; the repository’s numbers are the audit’s (`node scripts/health.mjs`, the evidence folders). Where a source could not be read, the gap is named rather than filled.


Research date: 2026-10-11. Repository baseline: commits 00843045 / 6e18a9c5 (numbers quoted from the repo audit are the site's own and carry no external citation).

The site should become a **tiered, GPU-resident renderer on three r186's node renderer**, in which the CPU submits a few hundred indirect or batched draws and compute shaders decide what is drawn, lit and streamed, because every UE5 technique that matters is reconstructable today on shipped WebGPU features except the ones that need hardware the web does not expose. Nanite's culling, LOD cut and visibility buffer map onto compute culling + `drawIndexedIndirect` + render bundles (Bevy's wgpu port renders ~445 M source triangles of instances in ~2.8 ms on an RTX 3080 with hardware raster); Lumen maps onto three's `SSGINode` for the near field, a DDGI-style probe grid for the mid field and the Enlighten atlases the project already reconstructs for the far field; Virtual Shadow Maps become cached cascades plus screen-space contact shadows; TSR becomes `TRAANode`/`TAAUNode` plus an RCAS sharpen; World Partition becomes a two-grid cell/HLOD manifest on the CDN; Niagara and Chaos become TSL compute particles and Rapier-in-a-worker with GPU debris. What cannot be reconstructed in 2026 is the software rasterizer (64-bit atomics are a Draft proposal, not in stable browsers), mesh shaders, ray tracing, bindless and multi-draw-indirect. The measured image-quality wins are mundane and cheap: never render below ~0.67x per axis without a temporal upscaler, apply the FSR mip-bias formula, serve UASTC instead of ETC1S for normal and roughness maps, set 16x anisotropy, use reversed-Z float depth, and light in physical units with EV100 exposure. The single largest performance trap is three's per-object uniform path (29 ms vs 7 ms CPU for 5k meshes, open issue #30560), which means the site's 700–1500 draw-call budgets measure the wrong thing: Mesh count, not draw count, must fall to the low hundreds. The WebGL2 node backend should be shipped as a reduced quality preset rather than a parity path; SharedArrayBuffer buys nothing on GitHub Pages because Rapier's wasm is single-threaded; and the static host wants many small content-hashed files on Supabase's cached-egress tier, not Range requests into one GLB.

## WebGPU, three r186, Rapier 0.21 and Wasm 3.0 are shipped; the GPU-driven extras are not

The platform the renderer targets is now broad but uneven. **Every major engine ships WebGPU by default on at least one platform**: Chromium since 113 on desktop and 121 on Android, Safari 26 (September 2025) on every Apple OS but only on OS 26 or newer, and Firefox 141 on Windows (July 2025) and 147 on Apple-silicon Macs (January 2026); Linux Chrome arrived for Intel Gen12+ in Chrome 144 and NVIDIA-on-Wayland in 147, with AMD and Firefox Linux/Android still outstanding ([gpuweb Implementation Status](https://github.com/gpuweb/gpuweb/wiki/Implementation-Status); [Chrome 144](https://developer.chrome.com/blog/new-in-webgpu-144); [Firefox 147 notes](https://www.firefox.com/firefox/147.0/releasenotes/)). caniuse puts global reach at **87.8%**, while web3dsurvey's 3D-site telemetry measures **83% of visitors with a working adapter, but only 74% on Android and 18% on Linux** ([caniuse webgpu](https://caniuse.com/webgpu); [web3dsurvey](https://web3dsurvey.com/webgpu)). The remaining WebGL2 audience is real: Chrome's own motivation statistics for compatibility mode say **31% of Windows Chrome users lack D3D 11.1+ and ~23% of Android users lack Vulkan 1.1** ([blink-dev I2S](https://groups.google.com/a/chromium.org/g/blink-dev/c/N3RlLGCOTJ4/m/loneRTlPBwAJ)). Compatibility mode shipped in Chrome 146 on OpenGL ES 3.1 but WebKit says it "isn't expected to ship in Safari", so it is a Chrome-only reach tool whose restrictions (no vertex-stage storage buffers, no format reinterpretation, no `sample_mask`) break deferred and GPU-driven paths anyway ([Chrome 146](https://developer.chrome.com/blog/new-in-webgpu-146); [webgpufundamentals compat](https://webgpufundamentals.org/webgpu/lessons/webgpu-compatibility-mode.html)).

The feature set that matters for a UE5-style renderer splits cleanly into "rely on", "detect and branch" and "assume absent". Reliable when WebGPU exists: core limits, `indirect-first-instance` (99.99% of reports), `depth32float-stencil8`, `shader-f16` (~94%), `texture-formats-tier1` (~93%), `float32-filterable` (~91%), `timestamp-query` (98.76%, but quantized to 100 µs in Chrome and uncertain in Safari) ([web3dsurvey](https://web3dsurvey.com/webgpu); [Chrome developer features](https://developer.chrome.com/docs/web-platform/webgpu/developer-features)). Branch on: `subgroups` (~68%, shipped Chrome 134), `texture-formats-tier2` read-write storage (~83%, Chrome 142, "motivated by porting Unreal Engine to the web"), `primitive-index` (~83%, Chrome 142), `dual-source-blending`, and the ASTC/ETC2-versus-BC split, which is roughly half and half so KTX2 must transcode to both ([Chrome 134](https://developer.chrome.com/blog/new-in-webgpu-134); [Chrome 142](https://developer.chrome.com/blog/new-in-webgpu-142)). Assume absent: **multi-draw-indirect** (gpuweb PR #2315 still an open draft; three's RenaudRohlinger asked for it in April 2026 citing BatchedMesh and got no date), **bindless** (Draft proposal created 2025-10-13; Brandon Jones' experiment post of 2026-10-06 says Chrome has only the sampling tier behind `enable-unsafe-webgpu` on Windows/Linux/Android, macOS "coming soon", no ship date), **mesh shaders** (issue #3015 open since 2022, "probably won't arrive soon"), and ray tracing (no proposal) ([gpuweb PR 2315](https://github.com/gpuweb/gpuweb/pull/2315); [bindless proposal](https://github.com/gpuweb/gpuweb/blob/main/proposals/bindless.md); [toji.dev bindless](https://toji.dev/2026/10/06/webgpu-bindless.html); [gpuweb #3015](https://github.com/gpuweb/gpuweb/issues/3015)). The one Nanite-critical primitive in flight is **`atomic-vec2u-min-max`** (64-bit min/max atomics as `vec2u`), which Chrome's roadmap ties explicitly to "software rasterization" and which the spec enum now lists, but the proposal page still says Draft while a Dawn commit calls it approved; no stable browser ship was verified ([Chrome roadmap](https://developer.chrome.com/blog/next-for-webgpu); [atomic-64-min-max proposal](https://github.com/gpuweb/gpuweb/blob/main/proposals/atomic-64-min-max.md)). WGSL itself grew a dozen language extensions in 2026, of which `immediate_address_space` (push constants, Chrome 149-150), `buffer_view` (one storage buffer punned into several arrays, Chrome 153-154), `fragment_depth` (early-Z-preserving depth writes, Chrome 155-156) and `linear_indexing` are directly useful for a GPU-driven pipeline ([Chrome 149-150](https://developer.chrome.com/blog/new-in-webgpu-149-150); [Chrome 153-154](https://developer.chrome.com/blog/new-in-webgpu-153-154); [Chrome 155-156](https://developer.chrome.com/blog/new-in-webgpu-155-156)).

Default limits bound the design. The spec floor is **8 storage buffers per stage, 32 bytes per sample of colour attachments, 256 MiB buffers, 128 MiB storage bindings, 16 sampled textures per stage, 16 KiB workgroup memory and 8192² textures**; real adapters sit far above on Windows but macOS and iOS cluster near the floor (only 31% of Macs report ≥16 storage buffers per stage, 64% of Macs and essentially no iOS reports 128 B/sample) ([gpuweb spec limits](https://gpuweb.github.io/gpuweb/#limits); [web3dsurvey storage buffers](https://web3dsurvey.com/webgpu/limits/maxStorageBuffersPerShaderStage); [web3dsurvey bytes/sample](https://web3dsurvey.com/webgpu/limits/maxColorAttachmentBytesPerSample)). A G-buffer of 32 B/sample (four rgba8 or two rgba16f) is therefore the portable layout and geometry pools should be chunked at 128 MiB bindings.

Budget a migration pass per upgrade.

The decisive performance fact about the node renderer is not GPU-side. In an independent r186 benchmark on an M1 Pro, **5,000 separate animated meshes cost three.js 29 ms of CPU on WebGPU versus 7 ms on the classic WebGLRenderer**, while 50k and 500k instanced objects tied or won at 1–2 ms; the tracked cause is issue #30560 ("Current UBO system has severe performance issues with many render items"), open since February 2025, still active in September 2026, with the maintainers' stated fix (shared buffers across groups of objects, updated once per render) not merged ([mvaligursky benchmarks](https://github.com/mvaligursky/webgpu-webgl-benchmarks); [issue #30560](https://github.com/mrdoob/three.js/issues/30560)). Even the WebGL2 node backend is 31% slower than WebGLRenderer with 80% more GL calls per frame on the same test. The site's draw-call budgets (350/500/700/1500 by tier) therefore measure a cost that is no longer the bottleneck; the number to drive down is the count of `Mesh` objects the renderer iterates, and the lanes that do that (BatchedMesh in `levelBatch`, which already cut Hoth from 209 draws to 80, `BundleGroup`, `instancedArray` compute in `particles/gpu.js`) are the ones to promote from optional to default. The WebGL2 fallback backend has no storage buffers (emulated via pixel buffer objects), no indirect draws, no subgroups, and emulates compute with transform feedback, so it is a degraded-visuals path by construction ([WebGLBackend.js](https://cdn.jsdelivr.net/npm/three@0.186.1/src/renderers/webgl-fallback/WebGLBackend.js); [GLSLNodeBuilder.js](https://cdn.jsdelivr.net/npm/three@0.186.1/src/renderers/webgl-fallback/nodes/GLSLNodeBuilder.js)).

Every UE5 system below decomposes into compute, indirect draws, render bundles, storage buffers/textures and temporal reprojection; only Nanite's software rasterizer and VSM's single-pass caster rendering additionally need 64-bit atomics. ### Nanite: culling and visibility buffer yes, software rasterizer not yet

Nanite breaks meshes into hierarchical clusters of up to 128 triangles, selects a cut of the DAG per view, culls with a two-pass hierarchical-Z scheme, and rasterizes small triangles in compute with a 64-bit `atomicMax` that fuses the depth test with a cluster/triangle payload, supporting only opaque and masked materials ([Epic, Nanite](https://dev.epicgames.com/documentation/en-us/unreal-engine/nanite-virtualized-geometry-in-unreal-engine)). The best-documented reconstruction on a WebGPU-shaped API is Bevy's meshlet renderer. Its 0.14 design uses meshoptimizer clusters of 64 vertices/64 triangles, METIS grouping, ~50% simplification per level with cumulative error, a GPU LOD test ("draw if own error projects < 1 px and parent's does not"), a cull pass against the previous frame's depth pyramid, **one non-indexed `draw_indirect` with vertex pulling** into an R32Uint visibility buffer plus R16Uint material depth, a depth pyramid in two dispatches, a second cull pass for late clusters, and one fullscreen triangle per material with a depth-equals test; the whole thing measured **~2.78 ms for 3,092 instances of a 144,042-triangle bunny at 2240×1260 on an RTX 3080**, with per-instance upload of ~0.025 MB versus the ~122 MB of per-cluster data that would otherwise cross PCIe ([JMS55, Bevy 0.14](https://jms55.github.io/posts/2024-06-09-virtual-geometry-bevy-0-14/)). Bevy 0.15 added a compute software rasterizer for clusters under 64 pixels on both axes and cut the bunny scene to **0.93 ms**, but it writes a 64-bit value per pixel (`bitcast<u32>(z)` high, `(cluster << 7) | triangle` low) and therefore requires `SHADER_INT64_ATOMIC_MIN_MAX`, which Bevy's maintainers confirm is "not supported on WebGPU at the moment" ([JMS55, Bevy 0.15](https://jms55.github.io/posts/2024-11-14-virtual-geometry-bevy-0-15/); [HN comment](https://hn.nuxt.dev/item/42974461)). Bevy 0.16's platform table confirms that on Web/WebGPU only "GPU transform" works, not its MDI-based culling or bindless ([Bevy 0.16](https://bevy.org/news/bevy-0-16/)).

Two web-native experiments calibrate expectations. Scthe's `nanite-webgpu` builds the DAG in-browser with meshoptimizer + METIS compiled to Wasm and software-rasterizes 98% of clusters in its Lucy-and-dragons scene, but lacking 64-bit atomics it packs a u16 depth into the 32-bit atomic and its own README calls the result "butchered" with "tons of artifacts like z-fighting or leaks" ([Scthe/nanite-webgpu](https://github.com/Scthe/nanite-webgpu)). Cinevva's three.js r184 visibility-buffer test on an M-series Mac found the hardware-raster visbuffer beat three's forward path at 50k grass instances (4.13 vs 5.51 ms) but lost at 200k (7.80 vs 5.44 ms) because the resolve pass randomly reads a 12.8 MB per-instance matrix buffer and Apple's TBDR already rejects occluded fragments; their verdict was to wait "until either discrete NVIDIA/AMD GPUs become the main target or a meshlet architecture makes a visibility buffer the natural output" ([Cinevva part 21](https://app.cinevva.com/blog/2026-05-06-open-world-browser-part-21-visibility-buffer)). Their Hi-Z cluster culling, however, works and is instructive: project the cluster bbox, pick the pyramid mip where the rect is ~2×2 texels, reject if behind the max depth, and make sure occluder proxies are canopy-sized rather than trunk-sized or the max-reduce erases them ([Cinevva part 22](https://app.cinevva.com/blog/2026-05-07-open-world-browser-part-22-clouds-and-meshlets)).

The reconstruction that follows: build the meshopt LOD DAG offline into fixed-size, quantised cluster pages (Bevy 0.15's 1/2⁴ cm position grid with per-meshlet bit widths, octahedral normals via `pack2x16snorm`, f16 error pairs), ship per-cell cluster buffers, run the Bevy 0.14 pass order in TSL compute with `IndirectStorageBufferAttribute` feeding `drawIndexedIndirect` inside a static `BundleGroup`, and gate a software-raster tier on `adapter.features.has('atomic-vec2u-min-max')`. Keep all indirect arguments in one buffer: Dawn on D3D12 injects a validation compute dispatch per distinct indirect buffer, measured at ~3 ms of a 6 ms pass with 412 separate buffers versus ~10 µs with one ([toji.dev indirect draws](https://toji.dev/webgpu-best-practices/indirect-draws)). Use `primitive-index` where exposed for the triangle id and Cinevva's flat per-vertex id (3x vertices) elsewhere. What is lost against Nanite is the software rasterizer's sub-pixel triangle throughput (a 2026 paper credits it with roughly 3x the hardware pipeline's) and quad-overdraw savings; what is retained is no CPU draw calls, LOD without pops, and occlusion ([CuRast, arXiv](https://arxiv.org/pdf/2604.21749)). three ships only `webgpu_compute_rasterizer` and `webgpu_struct_drawindirect` as examples; no official compute-culling-to-indirect example exists, so the site owns the whole scheme ([three.js examples](https://threejs.org/examples/files.json)).

### Lumen: three distance tiers, three web primitives

Lumen lights a surface cache of "cards" (12 per mesh by default) over several frames, traces screen space first, then each mesh's own distance field for the first two metres, then a merged global distance field to 200 m, and gathers through screen-space probes with a sparser world-space radiance cache; reflections trace dedicated rays below roughness 0.4; Epic budgets **8 ms at 30 fps and 4 ms at 60 fps at 1080p** for GI, reflections and volumetric fog on current consoles, with each lower quality level costing roughly half and the Medium tier swapping reflections for SSR, which "saves 1 ms on Xbox Series S" ([Epic, Lumen Technical Details](https://dev.epicgames.com/documentation/en-us/unreal-engine/lumen-technical-details-in-unreal-engine); [Epic, Lumen Performance Guide](https://dev.epicgames.com/documentation/en-us/unreal-engine/lumen-performance-guide-for-unreal-engine)). WebGPU has no ray-tracing API and three has no SDF scene, but the distance tiers translate. Near field: `SSGINode`, horizon-based (SSRT3/SSILVB), with presets Low 1 slice × 12 steps, Medium 2×8, High 3×16 when its temporal filter is on, and the temporal filter requires `TRAANode` ([SSGINode docs](https://threejs.org/docs/pages/SSGINode.html)). Mid field: a DDGI-style octahedral probe grid updated in compute against a coarse proxy; `speedball-gi` already does BVH-traced DDGI for three WebGPU ("prone to leaking but it is continuous"), and three ships `LightProbeGrid` with SH L2 baking plus an indirect-bounce option (r185) and `webgpu_vxgi_sponza` ([speedball-gi](https://cdn.jsdelivr.net/npm/speedball-gi@0.6.6/README.md); [LightProbeGrid.js](https://cdn.jsdelivr.net/npm/three@0.186.1/examples/jsm/lighting/LightProbeGrid.js)). Far field: the Frostbite Enlighten HDR atlases the project already exports, sampled per cell as static irradiance, exactly the role Lumen's HLOD1 Far Field plays out to 1 km. Reflections: `SSRNode` with its r185 spatiotemporal denoiser for roughness below ~0.4, with the probe or cubemap fallback for misses; note its `setEnvMap()` wants an equirectangular HDR with CPU-side image data, not a PMREM ([SSRNode.js](https://cdn.jsdelivr.net/npm/three@0.186.1/examples/jsm/tsl/display/SSRNode.js)). The cost model to copy is Lumen's amortisation: update N probes per frame (`NumProbesToTraceBudget`), evaluate the irradiance cache at 1/8–1/16 resolution, and pay full resolution only for the final integrate under TRAA. No published millisecond figure exists for `SSGINode` or speedball-gi at 1080p; the site's own perf-probe must supply it.

A note on the repo's post tiers: the high tier runs `ssgi(medium)` with SMAA rather than TRAA. Since `SSGINode`'s temporal filter needs `TRAANode` and the untemporal path needs `DenoiseNode`, whose own header warns it can "add quite some overhead", the high tier either pays the denoiser or ghosts; moving high to TRAA (or TAAU) resolves it and matches Epic's rule that TSR and GI are co-designed.

### Virtual Shadow Maps: cache cascades, add contact shadows

VSM gives every light a virtual 16k×16k map in 128×128 pages, directional lights a 17-level clipmap (levels 6–22, 64 cm to ~40 km), invalidates pages only when casters or lights move, and filters with SMRT (8 rays × 8 samples by default); it requires Shader Model 6.6 or `VK_KHR_shader_atomic_int64`, and Epic warns that non-Nanite casters make it "much more expensive" because each light needs its own draw-call pass ([Epic, VSM](https://dev.epicgames.com/documentation/en-us/unreal-engine/virtual-shadow-maps-in-unreal-engine)). The cheap web reconstruction is three's cascaded shadow maps with page caching at cascade granularity: `SunLight` (r186) renders two auto-fitted cascades into one atlas at 1024² each, `CSMShadowNode` gives three cascades for a `DirectionalLight` with reversed-depth support since r185, and the far cascades can be re-rendered every N frames or only on light/caster change ([SunLightShadow.js](https://cdn.jsdelivr.net/npm/three@0.186.1/examples/jsm/lights/SunLightShadow.js); [CSMShadowNode.js](https://cdn.jsdelivr.net/npm/three@0.186.1/examples/jsm/csm/CSMShadowNode.js)). `SSSNode` (r181) supplies the contact detail VSM's per-pixel resolution otherwise provides ("Use Shadow Maps for the foundation and Screen-Space Shadows for the details", max shadow length 1 m) ([SSSNode.js](https://cdn.jsdelivr.net/npm/three@0.186.1/examples/jsm/tsl/display/SSSNode.js)). A true paged VSM for the directional light is implementable without 64-bit atomics (mark needed pages from the depth buffer in compute, allocate into a physical atlas, render casters per page with scissor rects, sample through an indirection table), but each page needs its own draw list, so it costs like Epic's non-Nanite path; no WebGPU implementation was found. The repo's PCSS at 256 samples on ultra is the kind of per-pixel cost VSM's SMRT replaces with 64 samples; a Vogel-disk PCF (three's r182 default, with IGN) plus `SSSNode` will be cheaper and closer to the UE look than 256-tap PCSS, and r186 removed `PCFSoftShadowMap` on WebGPURenderer anyway ([Migration Guide](https://github.com/mrdoob/three.js/wiki/Migration-Guide)).

### TSR: TRAA at native, TAAU below it, and a sharpen pass neither node provides

TSR renders at 50–66% of output and reconstructs a display-resolution history; its convergence depends on the "feed" in megapixels per second (4K at 50% and 60 Hz = 124.4 MP/s, four frames to one sample per pixel), it rejects history with a convolution network and a flicker heuristic, and it costs **~0.79 ms at 100% / ~0.43 ms at 50% in Valley of the Ancient** and ~1.5 ms effective on PS5 in Fortnite; Epic calls anything below 50% "extreme upscaling" ([Epic, TSR](https://dev.epicgames.com/documentation/en-us/unreal-engine/temporal-super-resolution-in-unreal-engine)). three provides `TRAANode` (Halton 32, variance clipping, closest-depth velocity, MSAA must be off), `TAAUNode` (lower-resolution inputs via `PassNode#setResolutionScale`, 9-tap Blackman-Harris reconstruction, "an alternative to FSR2/3") and `FSR1Node` (EASU+RCAS, WebGPU `textureGather`, "only use FSR 1 if your application is fragment-shader bound") ([TRAANode.js](https://cdn.jsdelivr.net/npm/three@0.186.1/examples/jsm/tsl/display/TRAANode.js); [TAAUNode.js](https://cdn.jsdelivr.net/npm/three@0.186.1/examples/jsm/tsl/display/TAAUNode.js); [FSR1Node.js](https://cdn.jsdelivr.net/npm/three@0.186.1/examples/jsm/tsl/display/FSR1Node.js)). pmndrs/upscaler ports the FSR 2/3 architecture (Catmull-Rom history, variance clipping, reactive masks, luminance locks) to WGSL compute for r186+ and claims its fused passes are 6–76% cheaper than source-style FSR 3.1.5 graphs, but it is a 23-star project with no frame generation ([pmndrs/upscaler](https://github.com/pmndrs/upscaler)). Neither three node sharpens, so a `SharpenNode` (RCAS-like) belongs after the upscaler. The repo's lane U measurements already show the direction (5.7 ms TRAA → 5.1 ms TAAU at 0.77 scale at 1600×900; 11.3 → 9.1 → 7.7 ms at 4K on an RTX 5090). Translucency and panning materials need velocity or exclusion exactly as Epic documents, and TRAA/TAAU force the G-buffer to single-sample, which deferred shading wants anyway.

### Virtual texturing, World Partition, Niagara, Chaos

UE's streaming virtual texturing tiles every mip, requests tiles from GPU feedback (so popping is inherent), costs at least two fetches per sample and limits anisotropy with its 4-texel border; runtime VT renders BC-compressed layers at 8 uploads per frame in game ([Epic, SVT](https://dev.epicgames.com/documentation/en-us/unreal-engine/streaming-virtual-texturing-in-unreal-engine); [Epic, RVT](https://dev.epicgames.com/documentation/en-us/unreal-engine/runtime-virtual-texturing-in-unreal-engine)). A WGSL feedback VT is buildable (compute writes requested page ids, `mapAsync` readback, HTTP tile fetch, `writeTexture` into a compressed atlas, indirection lookup in TSL) but nothing shipped on the web was found and the readback adds a frame of latency on top of the network, so UE's documented popping would be worse. With 8192² textures and 16 samplers per stage as the floor, the practical counterpart is the per-cell texture-array row the repo already has in outline (`lod.js` colour maps 1024/512/256, ultra 2048), tiered per GPU class by `renderer.hasFeature()` for BC/ASTC/ETC2, using `CompressedArrayTexture` with `layerUpdates` (r185/r186) for low-mip-first uploads ([three.js releases](https://github.com/mrdoob/three.js/releases)).

World Partition keeps one persistent level hashed into a runtime grid (doc example 256 m cells, 768 m loading range), bundles cross-referencing actors, and hides unloaded cells behind HLOD actors (Instancing, Merged or Simplified) in their own coarser grid; Lumen's far field uses HLOD1 ([Epic, World Partition](https://dev.epicgames.com/documentation/en-us/unreal-engine/world-partition-in-unreal-engine); [Epic, HLOD](https://dev.epicgames.com/documentation/en-us/unreal-engine/world-partition---hierarchical-level-of-detail-in-unreal-engine)). The site's 128 m `CELL` and far-first stream order are already the fine grid; what is missing is the coarse HLOD grid that downloads first so the horizon exists in seconds. agargaro's octahedral impostors (16×16 hemi-octahedral views in a 2048 atlas, three nearest views blended) run 200k trees with meshopt LODs from 15–100 units and impostors beyond, and Bevy's lesson that direct `bytemuck` casts loaded a 5 MB mesh 8.5x faster than deserialisation (102 → 12 ms) argues for GPU-ready binary cell files over glTF JSON parsing ([agargaro impostors](https://discourse.threejs.org/t/a-forest-of-octahedral-impostors/85735); [JMS55, Bevy 0.15](https://jms55.github.io/posts/2024-11-14-virtual-geometry-bevy-0-15/)).

Niagara's GPU path, which Epic's pages would not render for the researchers, maps onto what three already ships: `instancedArray` compute particles (200,000 in `webgpu_compute_particles`, a 131,072-particle MLS-MPM fluid, 8,192 boids), depth-buffer collision from the previous frame, offline 3D SDF textures for distance-field collision, bitonic sort up to 64k or PlayCanvas's portable radix sort beyond, and an atomic alive counter driving the indirect draw count as in `webgpu_struct_drawindirect` ([three.js examples](https://github.com/mrdoob/three.js/blob/dev/examples/files.json); [PlayCanvas radix sort](https://api.playcanvas.com/engine/variables/RADIX_SORT_PORTABLE.html)). Epic's own caveats carry over verbatim: depth-buffer collision is "low-cost, but also low-accuracy", and particles that leave the screen vanish ([Epic, Niagara GPU collisions](https://dev.epicgames.com/documentation/en-us/unreal-engine/gpu-raytracing-collisions-in-niagara-for-unreal-engine)). Chaos splits destruction into a CPU rigid-body simulation of geometry collections (connection graph with strain thresholds, fields that anchor, sleep or break) and separate GPU effects, with a cache system for "smooth runtime replay of complex destruction"; the open-source Niagara Destruction Driver exists precisely because "the chaos physics runtime can be too expensive on the CPU to drive a lot of cosmetic destruction" ([Epic, Destruction Overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/destruction-overview); [RealtimeVFX](https://realtimevfx.com/t/open-source-unreal-engine-plugin-niagara-destruction-driver-turn-chaos-destructibles-geometry-collections-into-performant-gpu-niagara-particle-simulated-destructible-mesh/28818)). The web copy is the same split: Rapier owns chunks that can touch the player, break events push into a GPU debris buffer that never reads back, and scripted collapses stream as keyframe tracks.

The rest of UE5's look stack is mostly present in `three/addons/tsl/display`: bloom, DOF (DOOM-2016-style bokeh since r180), motion blur with `positionPrevious` (r186), lens flare, 3D LUT, film, chromatic aberration, godrays, GTAO/SSAO, SSR, SSGI, SSS, OIT, FXAA/SMAA/TRAA/TAAU/FSR1, plus clear coat, sheen, iridescence, transmission, a froxel volumetric lighting example (three passes at 128×128×64, "sub-1ms" in its author's words) and Forward+ clustered lighting ([three.js tsl/display](https://github.com/mrdoob/three.js/tree/dev/examples/jsm/tsl/display); [three PR 30530](https://github.com/mrdoob/three.js/pull/30530)). Custom WGSL is needed for the Hillaire-2020 sky LUT chain (Cinevva proved it in TSL on r184), Nubis clouds (1.1–2.0 ms half-res on an M1 in Cinevva's build), convolution bloom, local exposure, and a histogram-based eye adaptation ([Cinevva part 22](https://app.cinevva.com/blog/2026-05-07-open-world-browser-part-22-clouds-and-meshlets)). One number in the clustered-lighting benchmark deserves re-measurement before relying on `ClusteredLighting` at UE light counts: 512 clustered lights cost three.js 115–168 ms in Chrome versus PlayCanvas's 15 ms, while all engines ran 44–62 ms in Safari, which suggests a Chrome-specific pathology rather than a design limit ([mvaligursky benchmarks](https://github.com/mvaligursky/webgpu-webgl-benchmarks)).

## The blur is a pipeline defect list, and most of it is cheap to fix

The "1990s blur" complaint decomposes into a short list of measurable defects, each with a published fix; none of them requires a UE5 system. The first and largest is **rendering below device resolution and letting the browser stretch the canvas**: webgpufundamentals describes the browser taking a small canvas and filtering it up to CSS size, insists on `ResizeObserver` with `device-pixel-content-box` because multiplying CSS pixels by DPR is not exact, warns that Safari lacks `devicePixelContentBoxSize`, and suggests capping DPR at 2 since phones reach DPR 4 and "drawing 16x the pixels is literally up to 16x slower" ([webgpufundamentals resizing](https://webgpufundamentals.org/webgpu/lessons/webgpu-resizing-the-canvas.html)). When rendering below native is unavoidable, the stretch must be replaced by a real upscaler at a bounded scale: FSR2's own tiers are **1.5x Quality, 1.7x Balanced, 2.0x Performance, 3.0x Ultra Performance**, and Epic's TSR page says below 50% is only for >4K displays ([GPUOpen FSR2](https://gpuopen.com/manuals/fidelityfx_sdk/techniques/super-resolution-temporal/); [Epic TSR](https://dev.epicgames.com/documentation/en-us/unreal-engine/temporal-super-resolution-in-unreal-engine)). Digital Foundry's 2026 verdict on a PS5 title that upscales 1080p→4K with spatial FSR1 was "practically prehistoric" with "poor overall image quality", which is the fate of a `fsr1 elsewhere` chain at low scale ([Push Square summarising DF](https://www.pushsquare.com/news/2026/04/pragmata-looks-best-on-ps5-pro-says-tech-experts)). Against the repo: the `RESOLUTION_STEPS [1,.77,.67,.5]` ladder's last step is below both FSR2 Balanced (1/1.7 = 0.59) and Epic's floor, and the pace ladder `[1,.85,.72,.6,.5]` with `climb:false` can only ratchet down. Reading the FSR2 manual literally, every step also needs its own **mip bias of `log2(renderRes/displayRes) − 1`** (−1.58 at 1.5x, −2.0 at 2x); at native with TAA, Godot's guidance keeps the bias between −0.75 and 0 ([GPUOpen FSR2](https://gpuopen.com/manuals/fidelityfx_sdk/techniques/super-resolution-temporal/); [Godot guidance via commit](https://git.objectionable.solutions/Sara/behaviour-tree-test/commit/45bc1a379021017a841bc6a2f6afe03c6eb8040f)). Without the bias, textures sit a full LOD blurrier than the display grid, which is the complaint.

The second defect is anti-aliasing chosen for the wrong pipeline. **WebGPU supports exactly sample counts 1 and 4**, so the repo's canvas MSAA ladder of 8/4/2/0 by level is partly invalid on the target backend ([MDN GPUTexture.sampleCount](https://developer.mozilla.org/en-US/docs/Web/API/GPUTexture/sampleCount)). The decision rule is simple: forward with no post means MSAA 4x; any MRT, deferred, SSGI or upscaling means TRAA with MSAA off and two extra attachments (depth, velocity). Done well, TAA needs variance clipping with gamma near 1, velocity read at the closest depth in a 3×3 neighbourhood, Catmull-Rom history, a luminance-weighted ~0.05 source blend, and an 8–32 sample Halton jitter; three's `TRAANode` implements all of these, with a documented knob mismatch (code gamma 0.5–1 vs comment 0.75–2) where Tardif's 1.0 is the defensible default ([alextardif.com/TAA](https://alextardif.com/TAA.html); [TRAANode.js](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/jsm/tsl/display/TRAANode.js)). Specular shimmer on normal-mapped metal is not fixed by TAA; Filament's geometric specular AA (variance 0.15, threshold 0.2) and a roughness floor of 0.045 are the published defaults ([Filament Materials](https://google.github.io/filament/Materials.md.html); [Filament PBR](https://google.github.io/filament/Filament.md.html)).

The third defect is texture encoding. Basis's own documentation says ETC1S "don't work as well on normal maps" while UASTC is "near-BC7 grade" and "usable on all texture types including complex normal maps"; the KTX encoder's UASTC quality levels measure **43.45 dB (fastest) to 48.24 dB (very slow)**, with `--normal-mode` converting to a two-component X+Y layout and RDO lambda recommended at 0.25–0.75 for normals ([Basis Universal README](https://github.com/BinomialLLC/basis_universal/blob/master/README.md); [ktx encode](https://github.khronos.org/KTX-Software/ktxtools/ktx_encode.html)). The repo serves ETC1S packs and keeps UASTC as "a desktop job not served", which puts the smeared-normal defect in production. three's WebGPU backend gained BC4/BC5 in r180, so two-channel UASTC normals and roughness/metal maps can transcode to BC5 or EAC RG11 on the client ([r180 tag](https://github.com/mrdoob/three.js/releases/tag/r180)). Anisotropy is the companion fix: GLTFLoader leaves it at 1, and the repo's low/mid tiers set 1/4; 16 on every sampled texture with trilinear mips is the forum-proven cure for "sharp near, mud far" ([three.js forum](https://discourse.threejs.org/t/blurred-textures-at-a-distance-setting-anisotropy-levels-doesnt-effect-at-all/43899)). Texel density targets of 512–1024 texels/m for third-person environments come from one studio guide and a Siege anecdote, so treat them as a rule of thumb rather than a standard ([Stray Spark](https://www.strayspark.studio/blog/texture-resolution-guide-games-512-1k-2k-4k)).

The fourth defect is lighting that is not physically scaled. Filament's measured table puts sun plus sky at **120,000 lux at 10 am and sun alone at ~100,000 lux**, with exposure `1/(1.2·2^EV100)` and multiscatter energy compensation `1 + f0·(1/dfg.y − 1)` on specular IBL ([Filament PBR](https://google.github.io/filament/Filament.md.html)). Tone mapping is a choice of intent: Khronos PBR Neutral is 1:1 for base colours 0.08–0.8 with no hue shift and was built for "product photography use cases"; AgX is hue-stable filmic; ACES skews hue, which Blender developers document as the "Notorious Six" ([Khronos PBR Neutral](https://raw.githubusercontent.com/KhronosGroup/ToneMapping/main/PBR_Neutral/README.md); [Blender devtalk](https://devtalk.blender.org/t/blender-support-for-aces-academy-color-encoding-system/13972/209)). The repo's Neutral default is right for the classic portfolio page and arguably wrong for the game worlds, where a linear-then-LUT chain at exposure 1.4 reproduces Frostbite's look only if the LUT was authored for that curve; AgX plus a LUT after tone mapping is the hue-safe game path. Bloom should be thresholdless Jimenez bloom with a ~0.04 blend and a 13-tap Karis downsample rather than a thresholded blob ([LearnOpenGL bloom](https://learnopengl.com/Guest-Articles/2022/Phys.-Based-Bloom)).

Fifth, depth and LOD. Logarithmic depth writes `frag_depth` and "disables early-Z testing"; reversed-Z with `depth32float` achieves the same precision without the penalty and is what FSR2 "strongly recommends"; three's WebGPU backend uses `depth32float` for `reversedDepthBuffer` since r184 ([three.js forum](https://discourse.threejs.org/t/beware-of-logarithmic-depth-buffer-it-can-degrade-scene-performance/88495/10); [r184](https://github.com/mrdoob/three.js/releases/tag/r184)). LOD pops read as old; dithered crossfades hide them but "depend on Temporal AA", so they belong in the TRAA tiers and alpha-to-coverage in MSAA tiers ([Unreal forum](https://forums.unrealengine.com/t/dither-lod-in-blueprint-not-working/382139)). `KHR_mesh_quantization` with node-scale compensation saves up to 50% with "minimal quality loss" ([gltf-transform](https://gltf-transform.dev/modules/extensions/classes/KHRMeshQuantization)).

Finally, measurement. The repo's `gpu-parity` gate (PSNR ≥ 32, <2% pixels off) should move to NVIDIA FLIP, which "incorporates dependencies on viewing distance and monitor pixel size" and is a one-line install (`pip install flip-evaluator`), scored against a supersampled reference with TAA off ([NVlabs/flip](https://github.com/NVlabs/flip); [NVIDIA blog](https://developer.nvidia.com/blog/flip-a-difference-evaluator-for-alternating-images)). GPU time per pass comes from `timestamp-query`, which three exposes through the `trackTimestamp` backend option and `resolveTimestampsAsync()`, quantised to 100 µs in Chrome so only passes above ~1 ms are trustworthy in production ([three.js Backend docs](https://threejs.org/docs/pages/Backend.html); [Chrome 121](https://developer.chrome.com/blog/new-in-webgpu-121)). Frame pacing matters more than average rate: 30 fps with jitter "can feel like 20-25 fps", so log p99 frame time and frame-to-frame standard deviation and hold 60 with dynamic resolution rather than accept an uneven 30 ([Igor's Lab](https://igorslab.de/en/amd-crossfire-sli-nvidia-powercolor-2/3)). Epic's dynamic-resolution controller gives the constants: 50–100% range, a budget, a change threshold, a minimum change period "to avoid interfering with temporal jitter", and a panic drop after N consecutive over-budget frames, never touching the output resolution because that resizes the TAA history ([Epic, Dynamic Resolution](https://dev.epicgames.com/documentation/en-us/unreal-engine/dynamic-resolution-in-unreal-engine)).

## The best 2025–2026 web titles are GPU-resident, baked, and ruthless on phones

No shipping engine has flipped WebGPU to default. Unity 6.6 (1 September 2026) declared WebGPU "no longer experimental" and gates its GPU Resident Drawer, GPU occlusion culling, STP upscaling, VFX Graph particles and Adaptive Probe Volumes behind it, yet keeps WebGL2 as the default API with runtime fallback and ships a "WebGPU Device Filter" to deny specific browsers and GPUs ([Cinevva summarising Unity](https://app.cinevva.com/news/2026-09-01-unity-6-6-webgpu-production); [Unity Device Filter manual](https://docs.unity3d.com/6000.6/Documentation/Manual/webgpu-intro-device-filter-asset.html)). Babylon.js 9.0 (26 March 2026) added a Frame Graph claiming "40% or more" GPU memory savings in some cases and clustered lighting for "hundreds or thousands of dynamic lights", but still requires opting into `WebGPUEngine` ([Windows Dev Blog](https://blogs.windows.com/windowsdeveloper/2026/03/26/announcing-babylon-js-9-0)). PlayCanvas's Editor WebGPU remains an opt-in beta while its splat pipeline is WebGPU-first (v2.17.0 added GPU-driven splat sorting, f16 shaders and a global splat budget) ([PlayCanvas v2.17.0](https://github.com/playcanvas/engine/releases/tag/v2.17.0)). Godot's official web export is still WebGL2-only and single-threaded by default since 4.3; a third-party fork runs Forward Mobile on WebGPU at a self-reported 4–5x over Compatibility ([Godot docs](https://docs.godotengine.org/en/4.5/tutorials/export/exporting_for_web.html); [dwalter/godotwebgpu](https://github.com/dwalter/godotwebgpu)). The lesson for a three.js site is that the two-path quality matrix is industry standard, and the "looks installed" features are the same list everywhere: compute culling with indirect draws, GPU particles, clustered or probe lighting, temporal upscaling.

The best-documented three.js showcases share one recipe. **Bruno Simon's 2025 folio** runs TSL on WebGPU with WebGL fallback, merges ~78,400 single-triangle grass blades into one geometry, instances everything repeated, uses a palette texture instead of vertex colours, compresses with Draco plus ETC1S/UASTC, and on mobile drops water blur and DOF and lowers shadow-map resolution; its author's rule is "at 10 FPS, users leave" ([Awwwards case study](https://www.awwwards.com/brunos-portfolio-case-study.html)). **False Earth** (Codrops, April 2026) moved from WebGL to WebGPU+TSL for "over a million grass blades", packs 64 bytes per blade in four `vec4`, uses a compute pass that resets `instanceCount`, culls and appends visible indices into a `geometry.setIndirect()` buffer (about 80% of instances never reach the vertex shader), runs three LOD tiers with per-instance jitter against ring artifacts, and wraps `compileAsync` in a parallel compiler with timeout because "compilation can stall on some mobile GPUs" ([Codrops](https://tympanus.net/codrops/2026/04/21/false-earth-from-webgl-limits-to-a-webgpu-driven-world/)). **agargaro's forest** places 200k trees via `InstancedMesh2` with BVH culling, meshopt LODs to 100 units and octahedral impostors beyond ([three.js forum](https://discourse.threejs.org/t/a-forest-of-octahedral-impostors/85735)). **World Labs' Spark 2.0** deliberately stays on WebGL2 for "98%+ of devices", streams splats from seekable 64K-splat chunks with three fetch workers and a Rust→Wasm LOD traversal worker, and caps splat budgets at 500K–2.5M by device class with a 16M-splat GPU pool and LRU eviction ([World Labs](https://www.worldlabs.ai/blog/spark-2.0)). The independent r186 benchmark adds that three.js is "the smallest and fastest to start" (166 KB brotli, ~100 ms to first frame) and "advises instancing heavily" ([mvaligursky benchmarks](https://github.com/mvaligursky/webgpu-webgl-benchmarks)).

Three patterns recur. Lighting in shipped three.js showcases is baked or stylised with one directional shadow map; no shipped three.js title found uses real-time GI, so the site's Enlighten reconstruction plus SSGI is already ahead of the field. Post-processing is a desktop luxury that the best pieces switch off on phones. And nobody renders in a worker: Spark and Simon's staged loop keep rendering and simulation on the main thread and use workers for decode and LOD traversal, because with WebGPU the CPU savings that OffscreenCanvas used to buy come from compute culling and indirect draws instead. Mobile is a reduced preset everywhere (DPR clamp around 1–1.5, shadow map ≤1024, textures ≤1–2K, tone-map-and-bloom post), and the iOS 26.0–26.2 WebGPU canvas-flicker bug that made Construct disable WebGPU in Safari argues for a two-frame self-test on iOS before trusting three's automatic fallback ([WebKit bug 301627](https://bugs.webkit.org/show_bug.cgi?id=301627)). Published budgets have shifted from triangle counts to GPU-side budgets (Needle's 200,000-triangle full-screen LOD target, Spark's splat budget, PlayCanvas's global splat budget), and the only draw-call numbers are blog rules of thumb (desktop 2,000–5,000, mobile 150–500) that should be validated with `renderer.info` rather than adopted ([Needle gltf-progressive](https://engine.needle.tools/docs/gltf-progressive/); [abratabia](https://abratabia.com/mobile-browser-performance/reducing-draw-calls.php)).

## Streaming on a static host means many small hashed files, not Range requests

The economics are simple and favourable at portfolio scale. Supabase Pro includes **250 GB of egress and 250 GB of cached egress per month, charging $0.09/GB and $0.03/GB beyond**, so the repo's 19 MB `/galaxy` world or a 100 MB game fetched 2,500 times a month is free and every further thousand full downloads of a 100 MB title costs about $3 on the cached tier; Cloudflare R2 charges **$0 egress** at $0.015/GB-month storage and Bunny $0.01/GB in EU/NA, which are the hedge against a viral spike ([Supabase pricing](https://supabase.com/pricing); [Cloudflare R2 pricing](https://developers.cloudflare.com/r2/pricing/); [bunny.net pricing](https://bunny.net/pricing/)). The condition for the cheap tier is that every asset is public, unsigned and stable-URL, because Supabase's Smart CDN keys cache entries per signed token and revalidates on update within ~60 s ([Supabase Smart CDN](https://supabase.com/docs/guides/storage/cdn/smart-cdn)). The repo's `assetBase` bucket with a 12 s wait then local fallback already fits this; what should change is that URLs carry content hashes so CDN, browser cache and any Cache API layer all hit.

Range requests into a single GLB are the wrong tool. Stock GLTFLoader "first loads the entire bundle glb file and then starts the parse", the only range-streaming hook conflicts with the meshopt plugin, Babylon users found overlapping ranges re-download data, and the only Supabase statement on `Content-Range` is a 2021 beta post about audio and video with no current confirmation of CDN behaviour ([Lightrun mirror](https://lightrun.com/answers/mrdoob-three-js-gltfloader-http-range-requests-support); [Babylon forum](https://forum.babylonjs.com/t/why-using-http-range-requests-and-what-is-major-impact-w-o-or-with-using-it/24500); [Supabase storage beta](https://supabase.com/blog/storage-beta)). Every large-world web system that works does what 3D Tiles does: many small files loaded by viewport. Needle's `gltf-progressive` embeds the lowest of up to six mesh LODs and a 128 px texture preview and fetches the rest by screen coverage, turning a **56 MB asset into a 300 KB first paint** ("~90% smaller initial download"), skipping 8K textures on mobile ([Needle gltf-progressive](https://engine.needle.tools/docs/gltf-progressive/)). Spark's `.RAD` files are seekable 64K-splat chunks fetched by three workers, and SOG compresses a 1 GB splat PLY to 42 MB ([World Labs](https://www.worldlabs.ai/blog/spark-2.0); [PlayCanvas SOG](https://blog.playcanvas.com/playcanvas-open-sources-sog-format-for-gaussian-splatting/)). Unity's Progressive Asset Loading splits by scene and warns that without compression the output is larger than non-progressive ([Unity manual](https://docs.unity.com/en-us/engine/6000.6/manual/platform-specific/webgl/building-distribution/web-optimization/progressive-asset-loading)).

For the Frostbite worlds this means a manifest per cell with separate, hashed files for the HLOD proxy and impostor atlas, the root meshlet pages, each LOD level, and each texture mip row per GPU tier, with the coarse HLOD grid fetched first. The byte guidance is derived rather than sourced: keep each fine cell's first-paint payload (HLOD proxy, impostor atlas, lowest texture mips, root clusters) under 1–2 MB so a 20 Mbit/s connection fetches a 3×3 neighbourhood in about five seconds, and defer high mips and fine LODs by screen coverage. Store cell geometry as GPU-ready quantised binary rather than glTF JSON, following Bevy's 8.5x load-speed measurement. Wasm itself compresses to about a quarter with gzip, and Brotli precompression is what makes the first file small; verify whether Supabase compresses KTX2/GLB at the edge, because R2 and Bunny do and the researchers found no Supabase documentation on it ([Godot docs](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)). Texture tiers should follow adapter features rather than device class: web3dsurvey shows BC on 86.85% of reports but ASTC and ETC2 on only ~47% each, so ship both transcodes via KTX2 and detect with `KTX2Loader.detectSupport()` after `await renderer.init()` ([web3dsurvey](https://web3dsurvey.com/webgpu); [Migration Guide](https://github.com/mrdoob/three.js/wiki/Migration-Guide)).

The service worker's role is bounded. WebKit allows an origin up to 60% of disk, but iOS evicts script-writable storage including the Cache API after **seven days without interaction** unless the site is installed to the home screen, so the CDN cache is the real cache on phones and the repo's `sw.js` (installed packs only, GET only, no Range) is the right scope; extend it to precache the HLOD tier for repeat desktop visits rather than to emulate streaming ([WebKit storage](https://webkit.org/?p=14403); [web.dev storage](https://web.dev/articles/storage-for-the-web)). The repo's fetch pools (ultra 8, high 6, else 4; `levelStream parallel 4`) and timeouts (20 s + 1 s/MB) are sane; the gap is prefetch, since the audit records none beyond stream order, and a coarse-grid-first order with a screen-coverage priority queue (Needle's model) is the missing piece.

## Threads and SharedArrayBuffer buy little on GitHub Pages; Wasm pays only in hot kernels

GitHub Pages still cannot set headers: the 2022 community request for COOP/COEP has one staff reply from July 2023 ("No ETA") and users were still reporting the block in August 2026 ([GitHub community discussion](https://github.com/orgs/community/discussions/13309)). The only route to `crossOriginIsolated` is `coi-serviceworker`, which injects the headers from a same-origin service worker and reloads the page on first visit; its open issues include a Chrome-only "second run fails" report and a "flash of non-COI code" ([coi-serviceworker](https://github.com/gzuidhof/coi-serviceworker); [issues](https://github.com/gzuidhof/coi-serviceworker/issues)). Under `require-corp` every cross-origin asset, including the Supabase bucket, needs CORS or a `Cross-Origin-Resource-Policy` header; `credentialless` would relax that, but browser-compat data says **Safari desktop and iOS do not support it** and WebKit bug 230550 was still NEW on 2026-09-07 ([@mdn/browser-compat-data](https://cdn.jsdelivr.net/npm/@mdn/browser-compat-data@latest/data.json); [WebKit bug 230550](https://bugs.webkit.org/show_bug.cgi?id=230550)). Godot made single-threaded export the default for exactly these reasons ("always had compatibility issues" on macOS/iOS), Unity supports only native and Burst threads behind the headers and had WebGPU-plus-threads crashes on Safari 18.3, and Jolt's author proposed a separate multithreaded build with single-threaded fallback because "GitHub Pages doesn't support COOP/COEP" ([Godot docs](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html); [Unity multithreading](https://docs.unity3d.com/Manual/web-multithreading-intro.html); [JoltPhysics.js discussion](https://github.com/jrouwe/JoltPhysics.js/discussions/110)).

The decisive fact is that the site's physics engine cannot use threads anyway. Byte-level inspection of the shipped `rapier3d@0.21.0` wasm shows a non-shared memory section and glue with zero references to `SharedArrayBuffer`, `initThreadPool` or `Atomics`; Rapier's `parallel` feature is native-only, and the npm line's `-simd` flavour is the only speedup on offer (its wasm contains ~72,700 SIMD-prefixed opcodes versus 362 in the plain build) ([rapier_wasm3d_bg.wasm](https://cdn.jsdelivr.net/npm/@dimforge/rapier3d@0.21.0/rapier_wasm3d_bg.wasm); [rapier README](https://github.com/dimforge/rapier)). Dimforge's own statement is that "the fastest current npm package is 2x to 5x faster than the fastest 2024 package", and Godot's Jolt measurement puts wasm SIMD at 1.37–2x of frame time in real scenes ([Dimforge 2025 review](https://dimforge.com/blog/2026/01/09/the-year-2025-in-dimforge); [Godot blog](https://godotengine.org/article/upcoming-serious-web-performance-boost/)). So SAB would buy only zero-copy transform readback, which a double-buffered transferable `Float32Array(7·N)` achieves without isolation and works on Safari. Cinevva's measured worker architecture (input to worker each frame, authoritative positions back) estimates 0.1–0.5 ms per message hop and 0.5–2 ms per Rapier step for a few hundred bodies versus 5–15 ms for equivalent JavaScript, and found "the worker boundary did not dominate latency" ([Cinevva part 2](https://app.cinevva.com/blog/2026-02-25-open-world-browser-part-02-worker-physics)). The repo runs Rapier on the main thread at a fixed 1/60 step with up to four substeps; moving it to a worker with a fixed step, render-side interpolation, and `forEachActiveRigidBody` readback is the portable upgrade. Note that the 0.19→0.20/0.21 jump is a behaviour change (CCD against fixed colliders on by default, pose-based sleeping, `minIslandSize` removed), so the per-cell collider budgets (mid 400/30k tris, high 1000/60k, ultra 2000/100k) need re-tuning, and the `-compat` package embeds ~3 MB of wasm as base64 in a 4.3 MB `.mjs` that cannot stream-compile, so the Vite build should import the non-compat `rapier3d-simd` package ([bindings changelog](https://github.com/dimforge/rapier/blob/master/bindings/typescript/CHANGELOG.md); [jsdelivr listing](https://data.jsdelivr.com/v1/package/npm/@dimforge/rapier3d-compat@0.21.0/flat)).

Where else Wasm pays is narrower than enthusiasts claim. A 2025 Rust measurement on a `Float32Array` add shows the boundary dominating: **JS 1.403 ms, wasm-bindgen with a copied slice 1.623 ms (slower than JS), raw pointer export 0.353 ms, raw plus SIMD 0.231 ms** ([dev.to benchmark](https://dev.to/bence_rcz_fe471c168707c1/rust-webassembly-performance-javascript-vs-wasm-bindgen-vs-raw-wasm-with-simd-4pco)). The 4–6x only materialises for tight loops over typed data that already lives in Wasm memory; branchy object-graph code and anything dominated by three.js API calls stays within ~1.2x of JS. The candidates in this codebase are the terrain worker (noise, meshing), KTX2 transcoding (already Wasm), meshopt decode and simplification (three's `SimplifyModifier` is meshoptimizer-based since r186), and Rapier; cluster-DAG building belongs offline, not in the browser, despite Scthe's in-browser METIS. There is no zero-copy path from Wasm memory to a GPU buffer: `mapAsync`/`getMappedRange` hands JS a buffer the GPU owns, Wasm can only address its own memory, and the W3C group concluded in 2020 that shared-memory mapping "doesn't work", so the pattern is one copy from a typed-array view over Wasm memory via `queue.writeBuffer`, re-creating the view after any `memory.grow` because growth detaches every view ([public-gpu 2020](https://lists.w3.org/Archives/Public/public-gpu/2020Feb/0005.html); [MDN Memory.grow](https://developer.mozilla.org/en-US/docs/WebAssembly/Reference/JavaScript_interface/Memory/grow)). On iOS, pre-size `WebAssembly.Memory` and keep the heap in the low hundreds of MB: a 2024 WebKit report found only ~300 MB reliably available to Wasm pages, Safari kills the tab when `memory.grow()` fails, and a December 2025 report of Safari 26.2 leaking under ASYNCIFY builds was still open ([WebKit 269777](https://bugs.webkit.org/show_bug.cgi?id=269777); [WebKit 221530](https://bugs.webkit.org/show_bug.cgi?id=221530); [WebKit 304810](https://bugs.webkit.org/show_bug.cgi?id=304810)). Stay on 32-bit memory; memory64 is Safari-preview-only and SpiderMonkey documents it as slower because guard-page bounds-check elision is impossible ([SpiderMonkey memory64](https://spidermonkey.dev/blog/2025/01/15/is-memory64-actually-worth-using.html)).

WebGPU in a worker is defined (`WorkerNavigator.gpu`) and works on Chrome and Firefox, but no primary source confirms Safari 26 exposes a `webgpu` OffscreenCanvas context in a worker, and the shipped showcases all render on the main thread; a worker-hosted renderer is not a safe default in 2026 ([MDN WebGPU API](https://developer.mozilla.org/en-US/docs/Web/API/WebGPU_API)).

### 1. Fix the resolution ladder before anything else

Replace `RESOLUTION_STEPS [1,.77,.67,.5]` with a ladder whose floor is 0.67 (FSR2 Balanced is 1/1.7 = 0.59; Epic reserves below 50% for >4K) and make every step below 1.0 run through `TAAUNode` (or pmndrs/upscaler) followed by a `SharpenNode`, never through canvas stretch or FSR1 alone; set the texture mip bias to `log2(scale) − 1` per step and −0.5 to −0.75 at native under TRAA; replace `climb:false` with Epic's controller shape (history median, ≥5% change threshold, ≥8–16 frames between changes, immediate drop after 2–3 over-budget frames, output size never changed) ([GPUOpen FSR2](https://gpuopen.com/manuals/fidelityfx_sdk/techniques/super-resolution-temporal/); [Epic, Dynamic Resolution](https://dev.epicgames.com/documentation/en-us/unreal-engine/dynamic-resolution-in-unreal-engine)). The lane U numbers (5.7 → 5.1 ms at 0.77) show TAAU already pays. Gap: no published ms for `TAAUNode` on a mid-range GPU; FSR1's own tier factors were not confirmed from the fetched page; the 100 µs timestamp quantisation makes the controller coarse but adequate for a 12–16.7 ms budget.

### 2. Make the Mesh count, not the draw count, the budget

Promote `levelBatch` BatchedMesh from off-by-default lane U to the default for level geometry, give game materials the `userData.batchKey` the audit says they lack, wrap static cells in `BundleGroup`, and move the `instancedArray` compute pattern out of `particles/gpu.js` into props and foliage. The evidence is the r186 benchmark (29 ms vs 7 ms CPU at 5k meshes; instanced paths tie or win) and the still-open UBO issue #30560, whose maintainer comments say `Object3D.static` is meant to skip updates but the check in `RenderObject.js` is commented out ([mvaligursky benchmarks](https://github.com/mvaligursky/webgpu-webgl-benchmarks); [issue #30560](https://github.com/mrdoob/three.js/issues/30560)). Re-express the tier budget rows (calls 350/500/700/1500) as a Mesh-object ceiling in the low hundreds plus a GPU-time budget. Gap: no three.js-maintained benchmark exists and the per-frame NodeFrame cost is unquantified; measure with the repo's perf-probe on the real chip.

### 3. Serve UASTC normals, set anisotropy 16, use reversed-Z

Turn the UASTC desktop job into a served row for normal, roughness/metal and any data texture, encoded at `--uastc-quality 2–4` (47.5–48.2 dB) with `--normal-mode --linear` and RDO 0.25–0.75, keeping ETC1S for albedo; set `anisotropy = renderer.getMaxAnisotropy()` on every sampled texture in all tiers rather than 16/16/4/1; enable `reversedDepthBuffer` (which three maps to `depth32float` since r184) and drop any logarithmic depth ([ktx encode](https://github.khronos.org/KTX-Software/ktxtools/ktx_encode.html); [Basis README](https://github.com/BinomialLLC/basis_universal/blob/master/README.md); [r184](https://github.com/mrdoob/three.js/releases/tag/r184)). Gap: no normal-map-specific PSNR table across ETC1S/UASTC/BC7/ASTC was found; verify that the WebGPU sampler honours 16x by reading back the descriptor; confirm the TRAA depth thresholds (0.0005/0.001) still behave under reversed-Z.

### 4. Correct the AA ladder to what WebGPU supports

Sample counts are 1 or 4 on WebGPU, so the 8/4/2/0 MSAA ladder reduces to 4 for no-post tiers and 0 whenever TRAA, TAAU, SSGI or MRT is on ([MDN GPUTexture.sampleCount](https://developer.mozilla.org/en-US/docs/Web/API/GPUTexture/sampleCount)). Move the high tier from `ssgi(medium)+smaa` to TRAA (or TAAU), because `SSGINode`'s temporal filter requires `TRAANode` and `DenoiseNode` is costly; keep SMAA only on mid and FXAA/SMAA on the WebGL2 node backend where TRAA is unavailable ([SSGINode docs](https://threejs.org/docs/pages/SSGINode.html); [DenoiseNode.js](https://cdn.jsdelivr.net/npm/three@0.186.1/examples/jsm/tsl/display/DenoiseNode.js)). Set TRAA variance-clip gamma near 1.0 and write velocity for every skinned, instanced, alpha and panning material. Gap: no modern-hardware cost figures for SMAA 1x or MSAA 4x were found (only 2012-era GPUs).

### 5. Build the Nanite hardware path as the level renderer

Follow Bevy 0.14's pass order in TSL: offline meshopt LOD DAG per cell in quantised pages; compute cull against frustum, LOD cut and last-frame Hi-Z; indirect args in one buffer; `drawIndexedIndirect` from a static `BundleGroup` into an R32Uint visibility buffer plus material depth; SPD-style depth pyramid; second cull pass; per-material fullscreen resolve ([JMS55, Bevy 0.14](https://jms55.github.io/posts/2024-06-09-virtual-geometry-bevy-0-14/); [toji.dev indirect draws](https://toji.dev/webgpu-best-practices/indirect-draws)). Bevy's 2.78 ms on an RTX 3080 is the order of magnitude to expect, slower in TSL without subgroup SPD. Heed Cinevva's Apple-TBDR result: keep per-instance data compact and let the forward path win on integrated GPUs by tiering per adapter ([Cinevva part 21](https://app.cinevva.com/blog/2026-05-06-open-world-browser-part-21-visibility-buffer)). Gap: Karis's 2021 deck (page sizes, streaming requests) was unreadable to the researchers; no WebGPU meshlet renderer other than Bevy's native wgpu and Cinevva's grass case has published ms; no official three.js compute-culling example exists.

### 6. Reconstruct Lumen as three distance tiers

Keep `SSGINode` for the near field but raise its radius from 4 toward the node's default of 12 units under TRAA; add a compute-updated DDGI/SH probe grid (three's `LightProbeGrid` with indirect bounces, or speedball-gi's BVH tracing) for the mid field with a per-frame probe budget; sample the Enlighten atlases per cell as the far field; use `SSRNode` with its r185 denoiser only below ~0.4 roughness and fall back to probes, matching Epic's Medium tier that ships on Series S ([Epic, Lumen Performance Guide](https://dev.epicgames.com/documentation/en-us/unreal-engine/lumen-performance-guide-for-unreal-engine); [speedball-gi](https://cdn.jsdelivr.net/npm/speedball-gi@0.6.6/README.md)). Keep the SHED order (`[ssgi+denoise],[ssr],[godrays+lensflare],[ao]`) but shed the denoiser first once TRAA carries SSGI's temporal filter. Gap: Wright et al.'s 2022 slide numbers were unreadable; no ms for `SSGINode` or speedball-gi at 1080p on a named GPU.

### 7. Cache cascades, add contact shadows, drop 256-tap PCSS

Use `SunLight`/`CSMShadowNode` with the near cascade updated every frame and far cascades every N frames or on caster change, extend the far cascade toward the 140 m `ULTRA_SHADOW_FAR` with a static cached pass, add `SSSNode` for the first metre of contact, and replace the ultra tier's 256-sample PCSS with the r182 Vogel-disk PCF plus IGN, since r186 removed `PCFSoftShadowMap` for WebGPURenderer ([SunLightShadow.js](https://cdn.jsdelivr.net/npm/three@0.186.1/examples/jsm/lights/SunLightShadow.js); [SSSNode.js](https://cdn.jsdelivr.net/npm/three@0.186.1/examples/jsm/tsl/display/SSSNode.js); [Migration Guide](https://github.com/mrdoob/three.js/wiki/Migration-Guide)). Gap: Epic publishes no VSM page-pool size or pass ms; no WebGPU paged-shadow implementation exists to copy.

### 8. Stream a coarse grid first, hash every file, forget Range

Add a coarse HLOD grid (merged proxy plus octahedral impostor atlas per ~4 fine cells) that downloads before the 128 m fine cells, split each fine cell into separately hashed files (root clusters, LOD levels, texture mip rows per BC/ASTC/ETC2 tier), keep first paint under ~1–2 MB per cell (derived, not sourced), and leave Range requests alone ([Needle gltf-progressive](https://engine.needle.tools/docs/gltf-progressive/); [World Labs](https://www.worldlabs.ai/blog/spark-2.0)). Keep Supabase on the cached-egress tier with public stable URLs; plan R2 or Bunny as the spike hedge ([Supabase pricing](https://supabase.com/pricing); [Cloudflare R2 pricing](https://developers.cloudflare.com/r2/pricing/)). Gap: Supabase's Smart CDN behaviour for `Range` and Brotli/gzip of KTX2/GLB is undocumented; test with `curl -I -H 'Range: bytes=0-1023'`.

### 9. Move Rapier to a worker on the SIMD build and re-tune

Switch from `rapier3d-compat` to the non-compat `rapier3d-simd` package (stream-compiled, +0.77 MB unpacked), step in a module worker at a fixed timestep with a double-buffered transferable `Float32Array` readback over `forEachActiveRigidBody`, interpolate on the render side, and re-tune per-cell collider budgets and debris CCD (`maxCcdSubsteps = 0` for cosmetic debris) for 0.20/0.21's changed defaults ([Cinevva part 2](https://app.cinevva.com/blog/2026-02-25-open-world-browser-part-02-worker-physics); [bindings changelog](https://github.com/dimforge/rapier/blob/master/bindings/typescript/CHANGELOG.md)). Skip `coi-serviceworker` and SharedArrayBuffer: Rapier's wasm is single-threaded and Safari lacks `credentialless` ([WebKit bug 230550](https://bugs.webkit.org/show_bug.cgi?id=230550)). Consider Jolt only if a multi-core physics budget becomes necessary and hosting moves to a header-capable host. Gap: no 2026 benchmark of Rapier 0.21 SIMD vs Jolt vs Havok exists; awake-body capacity at 60 fps must be measured with `World.profilerEnabled`.

### 10. Light in physical units and pick tone mapping by intent

Author the sun near 100,000 lux and sky near 20,000 lux, derive exposure as `1/(1.2·2^EV100)` instead of the house constant 1.4, confirm multiscatter compensation and specular AO in the TSL BRDF, use AgX plus the Frostbite-matched LUT after tone mapping for the game worlds while keeping Khronos Neutral for the classic page, and switch bloom to the thresholdless Jimenez chain ([Filament PBR](https://google.github.io/filament/Filament.md.html); [Khronos PBR Neutral](https://raw.githubusercontent.com/KhronosGroup/ToneMapping/main/PBR_Neutral/README.md); [LearnOpenGL bloom](https://learnopengl.com/Guest-Articles/2022/Phys.-Based-Bloom)). Gap: whether three's TSL `BRDF_GGX` implements Fdez-Aguera multiscatter was not read; no controlled study quantifies GI vs tone mapping in perceived realism.

### 11. Ship a phone preset, an iOS self-test, and FLIP gates

Codify the published mobile recipe: DPR clamp ~1–1.5, shadow map ≤1024, textures ≤1–2K, post reduced to tone map and bloom, a 1–2 s startup probe to pick the tier, and a two-frame render-and-readback self-test on iOS 26.x before trusting WebGPU, falling back to the WebGL2 node backend otherwise ([Awwwards](https://www.awwwards.com/brunos-portfolio-case-study.html); [WebKit bug 301627](https://bugs.webkit.org/show_bug.cgi?id=301627)). Replace the PSNR ≥ 32 parity gate with FLIP against a supersampled reference and add per-pass `trackTimestamp` totals to perf-probe, trusting only passes above ~1 ms in production ([NVlabs/flip](https://github.com/NVlabs/flip); [Chrome 121](https://developer.chrome.com/blog/new-in-webgpu-121)). Gap: no published iPhone frame times for any WebGPU title; the iOS 26.x flicker fix release was not confirmed.

### 12. Gate the exotic tiers on adapter features and skip compat mode

Add a tier that enables the compute software rasterizer (Bevy 0.15 layout) when `adapter.features.has('atomic-vec2u-min-max')`, a subgroup SPD depth pyramid when `subgroups` is present, and tier-2 read-write storage textures where offered; detect WGSL language extensions via `wgslLanguageFeatures` and key the TSL shader cache on the feature set ([atomic-64-min-max proposal](https://github.com/gpuweb/gpuweb/blob/main/proposals/atomic-64-min-max.md); [Chrome 147-148](https://developer.chrome.com/blog/new-in-webgpu-147-148)). Do not build a third render path for Chrome's compatibility mode; its restrictions break the GPU-driven design and the WebGL2 node backend already serves those users ([webgpufundamentals compat](https://webgpufundamentals.org/webgpu/lessons/webgpu-compatibility-mode.html)). Gap: no stable-browser ship version for `atomic-vec2u-min-max`, bindless or multi-draw-indirect was verified; Firefox and Safari support for the 2026 WGSL extensions was not found.

## Conclusion

The research reframes the question. "Reconstruct UE5 on WebGPU" sounds like a feature-porting exercise, but the techniques that separate an installed AAA game from a web prototype reduce to a small set of architectural commitments that WebGPU already supports: the GPU decides visibility and LOD, geometry and textures live in GPU-resident pools fed by small hashed files, lighting is split by distance into screen-space, probe and baked layers, and resolution is a controlled variable with a temporal reconstructor rather than a browser stretch. The one UE5 pillar that remains out of reach, Nanite's software rasterizer, is also the one whose loss is least visible, since hardware rasterization of the same cluster DAG keeps every other benefit and Bevy's own author found software raster only 10–20% faster than mesh shaders in most scenes. The uncomfortable finding is that three's node renderer penalises exactly the scene-graph style this codebase grew up with; the migration is therefore less about shaders than about where instances are stored.

Two implications follow for sequencing. First, the cheapest work (resolution ladder, mip bias, UASTC normals, anisotropy, reversed-Z, AA ladder) removes most of the perceived blur before any GPU-driven code exists, and it can be verified with FLIP in the existing tooling within the current tiers. Second, the GPU-driven level renderer should be built as a feature-gated tier from day one, because the platform is still moving: 64-bit atomics, bindless and multi-draw-indirect are each one Chrome release from changing the cost table, and a renderer keyed on `adapter.features` and `wgslLanguageFeatures` absorbs those changes as new tiers rather than rewrites.
